## Context

支撐點資料在三個地方各有一份，生命週期不同：

| 位置 | 座標系 | 誰寫入 | 何時失效 |
|---|---|---|---|
| `SLAPrintObject::get_support_points()` | `sla_trafo` 空間 | backend（`slaposSupportPoints`） | `SLAPrint::apply()` 偵測 `sla_trafo_differs` → `invalidate_all_steps()` |
| `mo->sla_support_points` | raw object space | 手動 commit 路徑 | 隨 undo/redo 快照 |
| `GLGizmoSlaSupports::m_normal_cache` | raw object space | `reload_cache()` / `get_data_from_backend()` | **僅在 `mo->id()` 改變時** |

引擎層（第一列）的失效判定是正確的，且 `sla_trafo()` 排除 Z 旋轉與 XY 平移的設計恰好對應「哪些變換會改變列印方向」。問題在第三列：前端快取的失效條件與前兩者完全脫鉤。

`get_data_from_backend()` 還做了一次座標換算，把 backend 點拉回 raw object space：

```cpp
auto mat = po->trafo().inverse().cast<float>();
for (unsigned int i = 0; i < points.size(); ++i) {
    sla::SupportPoint sp = points[i];
    sp.pos = mat * points[i].pos;
    m_normal_cache.emplace_back(sp);
}
```

而渲染端用的是**完整**的 instance transform（含 Z 旋轉與 XY 平移）。兩者對「哪些成分屬於 trafo」的認定不同，是第二個可能的不一致來源。

## Goals / Non-Goals

**Goals:**

- 把「整排支撐點被拉長」定位到單一機制，而非同時套用多個猜測性修改。
- 前端支撐點快取的失效時機與 `SLAPrint::apply()` 的 `sla_trafo_differs` 判定對齊。
- `AutoGenerated` 點在方向改變後重新生成；`UserModified` 點保留。
- per-point 幾何參數在任何變換下都不被清除。

**Non-Goals:**

- 不改變 `sla_trafo()` 的定義或引擎層的失效判定。
- 不讓 Z 旋轉 / XY 平移開始觸發失效。
- 不改變 Points preview 的渲染路徑或效能特性。
- 不處理 undo/redo 快照內容的正確性。

## Decisions

### D1. 先診斷，再修正——三個候選機制與判別方式

「拉長」目前有三個可能來源。**實作的第一步是把它收斂到一個**，因為它們的修法不同，同時套用會讓驗證失去意義。

**候選 A：前端快取根本沒重載。** `data_changed()` 只在 `mo->id()` 改變時 `reload_cache()`；變換不改 ID。
- **判別**：在變換發生前後印出 `m_normal_cache.size()` 與前三顆點的 `pos`。若變換後與變換前逐位元相同，即為 A。
- **修法**：在 `data_changed()` 加入 `sla_trafo` 指紋比對（快取上次的 `sla_trafo(*mo)`，不等則重載），而非只比對 `mo->id()`。

**候選 B：`po->trafo().inverse()` 換算與渲染端的 transform 不對稱。** `sla_trafo` 排除 Z 旋轉與 XY 平移、包含 `relative_correction()` 與鏡像，左手座標時還多乘一次 `Scaling(-1,1,1)`（`SLAPrint.cpp:265-266`）；渲染端則用完整 instance transform。
- **判別**：取一顆點，手算 `sla_trafo⁻¹ · backend_pos` 再套用渲染端的 `instance_matrix_no_scale · (S · pos)`，與模型表面實際座標比對。若偏差恰為某個軸的縮放或反射因子，即為 B。
- **修法**：修正換算，使 `m_normal_cache` 中的 `pos` 確實落在 raw object space。

**候選 C：A + B 疊加。** 需分別修正。

**為何不直接兩個都改**：若 A 是唯一成因，動 B 的換算會引入新的座標錯誤且沒有回歸測試能抓到；反之亦然。診斷成本遠低於誤修的代價。

### D2. 失效條件對齊 `sla_trafo`，不自訂規則

前端要判斷「該不該失效」時，SHALL 使用與 `SLAPrint::apply()` 相同的依據：`sla_trafo(*mo)` 是否改變（含 `is_left_handed()`）。

- **為何不用「任何 instance transform 改變就失效」**：那會讓 Z 旋轉與 XY 平移也觸發重算，使用者只是把物件挪個位置就得重新生成支撐——比現況更糟，且與引擎層的判定不一致（引擎不會重算，前端卻清掉，兩邊再度脫鉤）。
- **為何不用 `mo->sla_points_status`**：它記錄的是「點從哪來」，不是「點還有效嗎」。兩者正交，都需要（見 D3）。

### D3. 依 `sla_points_status` 分流，而非一律清除

| 狀態 | `sla_trafo` 改變時 | 理由 |
|---|---|---|
| `AutoGenerated` / `Generating` | 失效並重新生成 | 這些點由 overhang 分析依列印方向算出，換方向後語意上已無效 |
| `UserModified` | **保留**，可提示使用者重新檢視 | 手動點存在 object space，隨表面一起轉動；是否仍適合支撐是使用者的判斷，不該代為刪除 |

- **為何不一律清除**：手動點是逐顆放置的高成本輸入。轉個角度就全部消失會嚴重損害可用性，且與上游 PrusaSlicer 的行為不一致。
- **為何 per-point 參數完全不動**：頭部直徑、penetration、contact 球半徑等描述的是支撐本身的尺寸，與列印方向無關。鏡像後它們仍然正確；清除只會讓使用者白白重設。

### D4. 快取失效時同步清除衍生狀態

`m_normal_cache` 失效時，與之一一對應的衍生狀態必須一併清除，否則會出現「新點配舊法線」：

- `m_normal_cache_normals`（由 `perf-sla-support-points-preview-render` 引入）——已在 `reload_cache()` 內清除，需確認新增的失效路徑也覆蓋。
- picking raycasters——`m_point_raycasters` 僅在編輯模式註冊，需確認變換發生於編輯模式時的處理。

**注意**：`m_head_model_cache`（幾何快取）以幾何參數為 key，與座標無關，變換時**不需要**清除。誤清只會造成一次無謂的重建，但也顯示對該快取語意的誤解，實作時應避免。

## Risks / Trade-offs

- **[診斷不完全就動手，修了症狀沒修根因]** → 這是本 change 最主要的風險。緩解：D1 明列三個候選與各自的判別方式，tasks 第 1 節為獨立的診斷階段，必須先產出結論才進入修正。

- **[失效條件過寬，Z 旋轉 / 平移也重算]** → 使用者僅移動物件位置即損失支撐點。緩解：D2 明訂以 `sla_trafo` 為唯一依據；驗收明列「Z 旋轉與 XY 平移不得觸發失效」。

- **[誤刪手動點]** → 不可逆的使用者資料損失。緩解：D3 的分流；驗收明列「`UserModified` 點在鏡像與非 Z 旋轉後仍存在且參數不變」。

- **[修正 B 引入新的座標錯誤]** → trafo 換算牽涉多個座標系，改錯會讓所有情境都壞掉（而非只有變換後）。緩解：若診斷指向 B，修正後必須回歸「未經任何變換」的基準情境，確認未退化。

- **[變換發生在 gizmo 開啟中 vs. 關閉中，路徑不同]** → 關閉時 `on_set_state()` 會把 `m_old_mo_id` 設為 −1，重開必然 `reload_cache()`；開啟中則不會。兩條路徑都需驗收。

## Migration Plan

無資料遷移、無檔案格式或 profile 變更。

回退策略：診斷階段無程式碼變更；修正階段依 D1 收斂到單一機制，修改範圍小且集中於 gizmo 前端，可獨立 revert。

## Open Questions

- 「拉長」屬於候選 A、B 還是 C？**這是進入修正階段的前置條件**，由 tasks 第 1 節解決。
- `UserModified` 點在方向改變後是否需要主動提示使用者？提示形式（notification / 對話框 / 無）為產品決策，待診斷完成後與需求方確認；本 change 預設不新增提示，僅保留點不刪除。
