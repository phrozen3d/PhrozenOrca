## Why

There is no separate release branch for the resin/FDM mixed build — the main (FDM) line keeps advancing, and engineers manually build the mixed variant off the current main-line checkout using the new `PHROZEN_ORCA_ENABLE_RESIN` flag (introduced in `phrozen-disable-resin-update-check`). Today that flag only gates the app-update check. The broader goal is: when building the **main (FDM) version** (flag `OFF`), none of the resin/SLA-specific functionality, parameters, or UI added by the ongoing PrusaSlicer-SLA-merge project should appear or be usable, to avoid accidental misuse by FDM-only users/printers.

## Audit Notes (2026-07-25)

While root-causing a crash report ("匯入/刪除 model 時，在 Objects 面板下 crash"), confirmed that the FDM/Resin switcher machinery is currently **not gated by `PHROZEN_ORCA_ENABLE_RESIN` at all** — it's unconditionally compiled and reachable in every build off this source tree today. This is concrete scope for the eventual audit:

- `MainFrame::create_preset_tabs()` (MainFrame.cpp) unconditionally constructs `TabSLAPrint`/`TabSLAMaterial` and calls `m_param_panel->rebuild_panels()` / `m_param_dialog->panel()->rebuild_panels()` at startup, regardless of flag or selected printer technology.
- `ParamsPanel::switch_process_tab_for_printer_technology()` (ParamsPanel.cpp) — the switcher's core rebuild path — is called from three sites in MainFrame.cpp: the explicit Phrozen mode toggle button handler, `on_presets_changed()` (fires on **every** printer preset reload, not just an explicit FDM↔Resin switch), and one more (~MainFrame.cpp:4452). None of the three are gated.
- `ParamsPanel.cpp` itself has no `#ifdef PHROZEN_ORCA_ENABLE_RESIN` anywhere: `m_mode_region`/`resin_objects_mode` branches in `set_active_tab()`, `sync_process_tabs_visibility()`, `refresh_tabs()`, `rebuild_panels()` all run unconditionally today.
- Just fixed a real bug caused by this: one `m_page_view`/`m_page_sizer` is shared across **every** Tab attached to a `ParamsPanel`, including `model_tabs_list`/`plate_tab` (the Objects/Plate per-item override tabs used by FDM too, not resin-only). The only place that actually destroys those shared wx controls is `ParamsPanel::clear_page()`, but it's reached from several call sites that only knew about their own Tab: `rebuild_panels()`, `TabPrinter::update_pages()` (Tab.cpp — fires whenever the printer technology actually changes, e.g. at startup or on a Phrozen FDM/Resin mode switch, and bypasses `rebuild_panels()` entirely), and `Tab::tree_sel_change_delayed()`/`update_current_page_in_background()` (normal category/tab navigation). None of them cleared `model_tabs_list`/`plate_tab`'s own Page/OptionsGroup pointers, so whichever path ran first left those tabs with dangling `ConfigOptionsGroup::sizer`/`custom_ctrl` pointers — next model import/delete while the Objects panel was active would AV in `OG_CustomCtrl::get_title_width()`. First attempt only patched `rebuild_panels()` and still reproduced (confirmed the `TabPrinter::update_pages()` path is what actually poisons the pointers, often before the user does anything). Final fix moved the protection into `ParamsPanel::clear_page()` itself (the single real teardown point) so every call path is covered uniformly. Fixed unconditionally (independent of the flag, see `Tab::clear_own_pages()` / `ParamsPanel::clear_page()`, commit `e367bb0025`) because the dangling-pointer defect itself is orthogonal to whether the flag is on or off.
- **Implication for this change**: gating only *fixes* under `PHROZEN_ORCA_ENABLE_RESIN` without also gating the call sites that trigger the vulnerable rebuild path gives a false sense of isolation — a flag-OFF build would still execute the same `rebuild_panels()`/`switch_process_tab_for_printer_technology()`/`TabPrinter::update_pages()` machinery unless those call sites (and ideally the SLA tab construction in `create_preset_tabs()`) are themselves wrapped. When this change's design/tasks are written, the switcher call sites listed above (MainFrame.cpp: mode-toggle handler, `on_presets_changed()`, ~line 4452), `TabPrinter::update_pages()`'s dual FFF/SLA page-set handling (Tab.cpp), and `create_preset_tabs()`'s unconditional `TabSLAPrint`/`TabSLAMaterial` construction should be treated as required scope, not optional cleanup — a flag-OFF build must not construct SLA tabs or run any dual-technology rebuild logic at all, or any future lifecycle fix in this shared area will again need to special-case both build variants.
- Also worth auditing when this change is implemented: any *other* place that reaches into the shared `m_page_sizer`/`m_page_view` or into `model_tabs_list`/`plate_tab` and assumes a single-technology world (e.g. `Page::activate()`'s unguarded `wxTheApp->CallAfter([this](){...})` at Tab.cpp ~6607, which captures a raw `Page*` — contrast with the safer `weak_ptr`/`shared_from_this()` pattern already used in `Page::update_visibility()`'s own CallAfter at Tab.cpp ~6564). Not fixed in this pass since it wasn't the confirmed cause of the reported crash, but it's the same class of lifecycle risk and should be checked during the full audit.
